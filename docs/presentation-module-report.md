# Presentation 模块报告

## 1. 模块定位

`presentation` 不是一个简单的“把文字丢给模型再出 PPT”的功能，而是研究工作流中的最后一环之一。它要把前面已经沉淀下来的实验方案、实验进展、结果图、论文草稿、审稿意见和项目阶段结论，转成可以直接汇报的材料。

核心目标有两个：

1. 让用户快速形成一份可讲、可改、可复用的汇报内容。
2. 让生成结果保持证据可追溯，而不是只生成一套好看的幻灯片。

## 2. 需求与场景梳理

### 2.1 组会汇报

这是当前最优先的场景。典型输入不是“我要做一个 PPT”，而是：

- 当前研究目标是什么
- 这周做了哪些实验
- 实验方案是否变动
- 结果图有哪些
- 目前遇到什么问题
- 下周要做什么
- 希望汇报给谁听，时长多少

系统要先把这些信息整理成结构化内容，再输出 PPT。

### 2.2 阶段汇报

适合中期检查、项目推进汇报、导师组内分享。

需要重点突出：

- 目标拆解
- 阶段性结果
- 下一步计划
- 风险与待决策项

### 2.3 论文汇报

适合 paper talk、投稿前组内过稿、答辩预演。

需要重点突出：

- 问题定义
- 方法框架
- 核心实验结果
- 消融和对比
- 结论与局限

### 2.4 Poster

Poster 和 PPT 的逻辑相近，但不是同一类产物。

- PPT 更适合“讲述”
- Poster 更适合“展示”

Poster 需要更强的视觉压缩能力，通常要求：

- 结构一眼可读
- 图大于字
- 文字更短
- 版面更稳定

### 2.5 复用型需求

未来这套模块还应支持：

- 中文/英文双语汇报
- 不同场景模板
- 不同听众层级
- 会议时长适配
- 生成后可二次修改

## 3. 功能需求

### 3.1 输入侧

至少要支持三类输入：

1. 手工结构化表单
2. 文件上传
3. 自然语言补充说明

建议的输入字段：

- 标题
- 汇报类型：组会 / 阶段汇报 / 论文汇报 / Poster
- 语言：中文 / 英文
- 听众：导师 / 组内 / 跨学科 / 会议评审
- 时长：5/10/15/20 分钟
- 当前实验目标
- 实验方案
- 实验进展
- 关键结果
- 图表文件
- 论文草稿或参考文献
- 遇到的问题
- 下周计划
- 希望重点强调的点

### 3.2 输出侧

至少输出以下产物：

- `SLIDES_OUTLINE.md`
- `SPEAKER_NOTES.md`
- `QA_BRIEF.md`
- `PPTX`
- 逐页生成的图片或预览图
- 可选 `Poster` 版本

如果是组会场景，优先级应该是：

1. 结构化大纲
2. 逐页讲稿
3. 图文页草图
4. 最终 PPT

### 3.3 质量要求

- 内容必须和实验材料对齐
- 每页只表达一个主信息
- 关键数据必须能追溯到原始输入或图表
- 大纲生成后要能人工确认
- 图片生成前不应直接跳过结构审查
- 输出应能被用户继续编辑，而不是黑盒成品

## 4. 推荐流程

### 4.1 组会汇报标准流程

1. 用户上传当前实验方案、进展、结果图、论文片段等材料。
2. 系统抽取结构化信息，生成汇报骨架。
3. 系统输出 `SLIDES_OUTLINE.md`，让用户确认。
4. 用户确认后，系统生成逐页内容与页面图片。
5. 系统组装 `PPTX`，同时输出讲稿和 Q&A brief。
6. 用户二次修改后再导出最终版。

### 4.2 组会汇报建议目录

一版常见且稳定的结构如下：

1. 标题页
2. 研究背景与目标
3. 当前实验方案
4. 已完成工作
5. 核心结果
6. 问题与风险
7. 下一步计划
8. 需要讨论的事项

这套结构足够覆盖大多数组会。

### 4.3 Poster 推荐逻辑

Poster 不建议直接复用 PPT 页数，而应做压缩：

- 保留问题、方法、结果、结论
- 删除过细的过程性叙述
- 图表优先
- 保留少量高密度文本

## 5. 调试与联调建议

### 5.1 最小可用版本

对于组会场景，最小可用版本不要求一次性把所有复杂能力都做满，但至少要做到：

- 能接收结构化输入
- 能汇总实验进展
- 能生成汇报大纲
- 能输出 PPT 草稿
- 能人工确认后再继续

### 5.2 调试重点

1. 输入是否足够结构化
2. 大纲是否贴合场景
3. 每页是否信息过载
4. 图和结论是否对应
5. 讲稿是否和页面一致
6. 最终导出的文件能否正常打开

### 5.3 建议的测试层级

- 结构测试：检查输入字段是否完整
- 内容测试：检查大纲是否覆盖背景、方法、结果、计划
- 路由测试：确认 `/present` 会进入 presentation 流程
- 生成测试：确认 PPTX、notes、QA brief 都产出
- 回归测试：修改一轮后不破坏旧产物

## 6. 对当前系统的实现建议

当前 `presentation` 模块建议明确成一个“分层流水线”：

1. `input normalization`
2. `story extraction`
3. `outline generation`
4. `human approval`
5. `slide rendering`
6. `deck assembly`
7. `QA and export`

这样做的好处是：

- 调试更清楚
- 中断后容易恢复
- 产物更适合追踪
- 后续扩展 Poster 更容易

## 7. Skill 化建议

这部分适合做成 skill，而且已经非常适合 skill 化。

原因很直接：

- 流程稳定
- 产物稳定
- 输入模板稳定
- 可复用性高
- 很适合“先大纲，再图像，再成品”的固定工作流

建议把它作为一个独立的 presentation skill，或者在现有 `research-presentation-pipeline` 上继续扩展，重点补齐：

- 组会模板
- Poster 模板
- 输入表单规范
- 大纲审查规则
- PPT 生成校验

## 8. 结论

对科研 agent 来说，presentation 模块的关键不是“会不会生成幻灯片”，而是“能不能把实验材料整理成可汇报、可审查、可复用的成果链”。

如果按当前目标推进，建议优先把组会汇报打通成标准路径：

`实验方案/进展上传 -> 结构化整理 -> 大纲确认 -> 页面生成 -> PPT 输出`

Poster 可以作为同一条流水线上的第二输出形态，在组会场景稳定后再并行展开。
