# Paper Agent 用户工作流合同

## 命令语义

Chatbox 面向论文工作的显式命令只有五个：`/idea`、`/review`、`/plan`、`/write`、`/rebuttal`。其中 `/review` 始终表示 **literature review（文献综述）**，不表示同行审稿；模拟审稿与投稿前终检是工作流内部质量阶段，不是额外命令。

| 命令 | 用户目标 | 默认输入 | 核心输出 | 内部质量环节 |
|---|---|---|---|---|
| `/idea` | 提出、比较、验证选题 | 兴趣方向或已有证据 | 候选、反证、`idea/FINAL_IDEA.md` | 新颖性/可行性压力测试 |
| `/review` | 建立文献证据，或写一篇综述 | 主题，或用户的文献包 | 检索记录、证据图、研究空白；需要时为综述稿 | 引用闭合、主题综合审查 |
| `/plan` | 把选题和证据转为研究/论文方案 | `FINAL_IDEA`、综述证据或直接目标 | 研究蓝图、实验计划、章节/论证结构 | 风险与证据缺口检查 |
| `/write` | 从研究材料写论文，或改写已有稿件 | 方案、方法、结果、图表、文献、现有稿 | 写作包、草稿、修订稿、导出件 | 自审、修订、终检 |
| `/rebuttal` | 审核稿件，或根据审稿意见返修和回复 | 稿件；返修还需编辑/审稿意见 | 审稿诊断，或返修稿、回复信、Revision Ledger | 逐条闭合、终检 |

## `/review` 的两种清晰模式

`/review` 的首要职责是把文献变为可用证据；是否生成“综述文章”由用户目标决定，而不是由命令名猜测。

### A. 证据模式：为选题、方案或普通论文服务

适用：还没有足够材料，或当前只需要找文献、理解领域、形成研究缺口。

示例：

```text
/review 检索 2020 年以来 LLM 多智能体系统的可靠性与成本证据，供后续选题使用
```

平台执行：检索协议 → 多查询检索/去重/筛选 → 可公开全文与机构访问交接 → 证据图与研究空白。后续接 `/idea`、`/plan` 或 `/write`。

### B. 综述稿模式：交付一篇可继续编辑的 literature review

适用：用户明确说“写综述/综述文章/叙述性综述/系统综述草稿”，或上传了文献包并要求主题化综合。

示例：

```text
/review 使用上传的文献包写英文叙述性综述；按机制、评测和部署证据组织，保留冲突与局限
```

平台执行：先完成与证据模式相同的可追溯材料准备，再生成主题综合、taxonomy、synthesis matrix 和引用闭合产物。若用户提供完整本地语料并明确“仅使用/不要外检”，平台只综合该包；否则默认仍补充外部检索。

## 用户已有材料时怎么走

| 手头已有内容 | 推荐请求 | 是否外检 |
|---|---|---|
| 只有研究方向 | `/idea`，再 `/review` | 是，按需 |
| 一批论文/PDF/BibTeX，想写**独立综述** | 上传后 `/review 使用上传文献包写综述` | 默认可补检；说“仅使用上传语料”则否 |
| 一批论文，想写普通研究论文的 Related Work | 先 `/review` 建立证据，再 `/write 根据本会话证据写 Related Work 和全文` | 视综述阶段而定 |
| 方案、方法、结果、图表，想写研究论文 | `/write 根据上传的方案、结果和图表写……` | 否，除非明确要求补充文献 |
| 已有草稿，想润色/重构 | `/write 润色/诊断并修改上传稿件` | 否 |
| 已有稿件但还没有外部意见，想先挑问题 | `/rebuttal 审核当前稿件并给出可执行修改意见` | 否 |
| 编辑信和审稿意见齐全 | `/rebuttal 根据上传审稿意见准备返修与回复` | 否；绝不编造新实验 |

## 典型真实用户链路

```mermaid
flowchart LR
  I["研究方向或问题"] --> IDEA["/idea：选题与反证"]
  IDEA --> REVIEW["/review：检索、筛选、证据图"]
  REVIEW --> PLAN["/plan：研究设计和论文结构"]
  PLAN --> WRITE["/write：证据/材料→稿件"]
  WRITE --> INTERNAL["内部：自审→修订→终检"]
  INTERNAL --> RB["/rebuttal：审稿意见→返修/回复"]
  RB --> FINAL["内部：逐条闭合→终检"]
```

用户可从任何有材料的节点直接进入：上传真实文献包后从 `/review` 开始；已有结果后从 `/write` 开始；已有投稿意见后从 `/rebuttal` 开始。每一步都在同一 session 的 `agent-workspace/local/<session_id>/` 留下可交接产物，后续命令优先复用而非重新编造上下文。

当 `/idea` 或 `/review` 已经产生上游知识资产时，`/plan` 会读取这些资产并生成 `Content/SESSION_KNOWLEDGE_PACKAGE.json` 与 `Content/HANDOFF_CONFLICT_REVIEW.md`。后者只登记来源、边界和候选冲突，要求作者确认取舍；它不会替用户把相互矛盾的 Idea、证据或 Wiki 结论静默合并。确认后的计划才作为 `/write` 的结构与证据边界输入。

## 风格、期刊和学位论文

在 `/review` 或 `/write` 中写明领域、语言和目标期刊即可，例如“英文、Nature 风格”“中文 CSSCI 规划期刊”“中文博士学位论文第三章”。若上传已发表范文，平台只提炼结构、章节职责、引证习惯、术语和图表规则；不复制范文句子或论证。指定期刊而没有范文时，平台可检索其官方 author guideline 和代表性论文，记录来源与日期；无法核实的期刊规则必须标注为待作者确认。

学位论文的章节润色保留原有章节层级和研究逻辑；不会被强行改为 Abstract–Method–Conclusion 的期刊结构。
